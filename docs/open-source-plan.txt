Release boundary
Keep private development history private. Export only the approved tracked tree
into separate public history; never push private branches, tags, notes, PR refs
or historical Git objects to the public repository. For later releases, apply the
reviewed tree changes on public history. Record private candidate, public commit,
tag and checks separately. A public commit does not inherit private test evidence
merely because it was exported from a tested tree.

Original purpose
Build an opinionated, extensible meme library for individuals self-hosting their
own instance. The first release serves one owner, protects their archive, and
allows deliberate public sharing of selected media. It is not a hosted service
for unrelated users or a team-permissions product.

1. Establish the source alpha
- License decision: 0BSD. Maintain asset provenance and third-party notices,
  contribution expectations, and a private security-reporting route.
- Review the new repository's content for publication. Fresh history avoids
  importing old commits but does not itself establish publication readiness.
- Make the supported platform, setup, feature availability, and AI data flows
  explicit. Preserve the useful developer guide and avoid competing guides.
- Gate: a clean checkout can run the documented isolated mock workflow without
  production secrets or services, and publication clearance is complete.

2. Deliver a portable private instance
- Provide one Compose-based full-feature deployment with the online API,
  worker, PostgreSQL, Redis, explicit storage, and an authenticated entry point.
- Keep local SQLite/mock tooling clearly scoped; it is not feature-equivalent
  to the full online application. Telegram sync can be optional for users who
  begin with uploads.
- Configured durable owner identity now retains drafts and curation across
  browsers and cookie loss. Follow deploy/community/README.md for provisioning
  and recovery; this remains a single-owner deployment, without team accounts.
- Make public sharing optional and explain which media/context goes to AI
  providers, including private uploads and retained error records.
- Gate: a fresh operator installs without the original host layout, accesses
  the authenticated library, and retains data across restart. Unauthenticated
  library/API/media access fails; selected published shares work as intended.

3. Verify v0.1 workflows and recovery
- Resolve the public-share caption/summary test contract and include modern
  frontend workflows in the documented CI/test path.
- Exercise import, browse, metadata edit, remix, save, share, recall, delete,
  restart, and a declared supported upgrade using disposable data.
- Document and prove a consistent backup and restore, including the separately
  protected signing/configuration material needed for supported identities and
  links. Reconcile any completed upstream backup work before duplicating it.
- Gate: restore a second disposable instance with originals, metadata, lineage,
  jobs, and supported owner/share behavior intact.

4. Prove extensibility with concrete use cases
- First allow mixed provider routing using the existing adapters, with coherent
  circuit recovery, embedding/classification identity, and queued-job provenance.
- Add stable folder ingestion when implemented; the fixture importer has
  positional identity and is not a production folder-sync contract.
- Add bounded prompt/style profiles with structural schemas retained in code,
  effective prompt identity, and an explicit derived-data refresh policy.
- Prefer narrow helpers and additive changes. A plugin framework, new provider,
  neutral-source schema rewrite, and teams/RBAC are not first-release goals.

Next milestone
A new individual installs an isolated instance, uses their own media, and
recovers the library from backup without help from the original operator.
Stages 1-3 establish that claim; stage 4 demonstrates focused extensibility.
